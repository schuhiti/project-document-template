# knowledge種別の設計で却下した代替案

`knowledge`種別（判断も手順も伴わない確定した内容）を設計する過程で、次を検討し却下した。再検討する際の重複調査を避けるための記録。

- **`domain`タグ**: 知識の大半がドメインに関するものになる想定のため、全件に同じタグが付き分類として機能しない。却下
- **`class`（単一値の分類フィールド）**: 実際の知識は複数の性質を併せ持つことが多く（例: 外部APIの用語集はexternalでもvocabularyでもある）、単一値では表現できない。複数値を持てる`tags`を採用した
- **`structure`/`interface`等の固定タグ候補**: 実例が無いまま語彙を先に決めると、後で重なりや過不足に気づいて直すことになる。tagsは自由記述のまま運用し、実例が溜まってから抽出する方針にした
- **TEMPLATE.mdの用意**: 話題ごとに本文の構造が全く異なり、固定の見出しを与えるとむしろ実態に合わない構造を押し付けることになる。ADRやtodoのような、frontmatterに固有の運用規則がある種別とは性質が違う
- **`design`統合時に`tags: [design]`等を推奨する案**: 実際には移行すべき既存のdesign文書が1件も存在しなかった。実例が無いまま特定のtag値を推奨するのは、却下した`domain`タグと同じ誤りになる
- **「確定した事実」という呼称**: 議論を通じて決めたドメイン用語の定義など、発見された事実に限らない内容も含むため、「内容」という語に統一した
- **内部/外部（自システムか外部か）を種別の境界とする案**: この区別自体は他のtag候補と同列の一変数に過ぎず、種別を分ける基準にはならない
