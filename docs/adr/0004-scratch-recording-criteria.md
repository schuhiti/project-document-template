# ADR-0004: `.dev/scratch/`の記録基準と運用を確定する

## Context
`.dev/scratch/`は当初「未確定の論点の下書き」置き場として設計したが、運用中に「作業ログ」的な記録（却下した方針、原因判明の知見）も必要になった。何でも記録すると肥大化するため、書く価値の基準と、下書きと知見を区別する仕組みの要否を検討した。

## Decision
`.dev/scratch/`は下書きと知見を`type`等で区別せず、単一の`type: scratch`で運用する。書く価値の基準は「これを記録しないと将来同じ時間を使って再発見する羽目になるか」とし、却下した方針とその理由、非自明な根本原因の結論（判明した瞬間に書く。調査の一部始終は書かない）のみを対象とする。定型的な成功作業・時系列の活動記録・コード固有の知見・ADRの「Alternatives Considered」と重複する内容は書かない。ファイルは論点ごとにkebab-caseのスラッグで作成し（連番なし）、同じ論点への追記か新規ファイルかは論点の同一性で判断する。`index.md`はファイル名と1行説明のみ（Status列は持たない）とし、ファイルを削除した際はindex.mdの該当行も削除する。

## Consequences
記録の判断基準が明確になり、Handoffで一度経験した肥大化がscratch側で再現するリスクを抑えられる。一方、「再発見コストがあるか」の判断は主観に委ねられ、書くべきものを書き逃すリスクは残る。

## Alternatives Considered
下書き用と知見用でfrontmatterに`kind`フィールドを設ける案は、更新方式（追記）が実質同じであることと、Handoffのポインタ有無で活動中/完結の別がすでに表現できることから、情報の重複になるため却下した。
