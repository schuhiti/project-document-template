# 文書種別ごとの運用

場所（パス）は`AGENTS.md`のドキュメント参照表を参照。ここでは重複させない。

「セッション」とは、(1)作業の中断・終了直前、(2)コンテキスト圧縮の前後、という時間的に区切られた区間を指す。(3)大きな決定があったこと自体は区切りを意味しない（Handoffは更新するが、todo.mdの棚卸しは行わない）。

ADRを引用する、またはADRの内容が生きた文書に反映されているか確認する際は、そのADRが後の別ADRで補正・補足されていないかを確認し、あれば両方を合わせて内容を確認する。可能なら、生きた文書側は特定のADR番号への依存自体を無くす（内容を直接書くか、もう引用しなくてよい形にする）方が、後から別のADRが補正するたびに引用を追跡し直す必要がなくなり安全である。

| type | 書く契機 | 更新方式 | サイズ規律 | 破棄・整理 | 遷移 |
|---|---|---|---|---|---|
| `premise` | 確定前提の新規確定・変更時のみ | 上書き | 確定前提のみ。検討中のものは書かない | 前提が変われば置き換え | なし |
| `adr` | 本当に複数の選択肢の比較と後戻りコストを伴う、アーキテクチャ上重要な決定の場合のみ。多くの決定は、それを反映する文書（documentation-rulesの該当箇所、knowledge等）に理由を直接書き添える方が軽量で、却下した代替案は別の`knowledge`エントリへのポインタとして残せる。過去の決定の遡及記録は、再検討されるリスクがある場合のみ行う | 新規作成のみ。Statusフィールドのみ例外的に可変（supersede時に更新）、他の項目は不変 | 6項目、各1段落以内（Title/Status/Context/Decision/Consequences/Alternatives） | しない（歴史として保持） | `scratch`/GitHub Discussionsからの受け皿 |
| `knowledge` | 判断も手順も伴わない確定した内容を書く必要が生じた時。書く契機は`scratch`行と同じ再発見コストのテスト（「これを記録しないと将来同じ時間を使って再発見する羽目になるか」）を適用する | 上書き（内容が変われば書き換え） | 個別の話題単位。まとまった仕様書・設計書はここに丸ごと置かない | 不要になったら削除 | `scratch`からの受け皿 |
| `skill` | 手順・判断基準が確立した時（同じ指摘の繰り返し等がトリガー） | 上書き | 簡潔に保つ | 手順が変われば書き換え、不要なら削除 | `scratch`から確立したものが移る |
| `scratch` | 未確定の論点が生まれた時、または「これを記録しないと将来同じ時間を使って再発見する羽目になるか」に該当する出来事（却下した方針とその理由、非自明な根本原因の判明）が起きた瞬間。定型的な成功作業・時系列の活動記録・コード固有の知見（コードコメントの方が発見されやすい）は書かない | 追記。同じ論点なら既存ファイルに追記、独立した論点なら新規ファイル（kebab-caseスラッグ、連番なし） | 個別ファイルに分割し肥大化を避ける | 定期的なtriageで確定文書（premise/knowledge/Issue/`.dev/todo.md`）へ移す、または破棄。ファイルを削除したら`index.md`の該当行も削除する | `.dev/handoff.md`からはポインタで参照される。検討中の内容そのものはここだけが持つ |
| `handoff` | (1)セッション/作業の中断・終了直前、(2)コンテキスト圧縮の前後、または(3)再開に支障が出る大きな決定があった時のみ。同一セッション内の細かい進行では更新しない | **完全上書き**（差分でなく丸ごと差し替え） | 常に「今の状態」のみ。目安は数十行。進行中の検討・作業の内容そのものは埋め込まず、`.dev/scratch/xxx.md`・`.dev/todo.md`やIssue番号へのポインタに留める | 定住先に移せた節は即削除。「暫定的に保持」を居座りの言い訳にしない | 全定住先への一時避難所。長居させない |
| `template` | 文書種別のひな形が確立した時 | 上書き | 対象種別のひな形のみを持つ | 種別の運用が変われば書き換え | なし |
| `index` | ディレクトリ作成時、最初から置く | 追記（ファイル追加時に1行追加） | ファイル一覧+1行説明のみ。ただし`docs/adr/`の索引はStatus列を追加してよい（supersedeの追跡に価値があるため） | 対応ファイルが消えたら該当行を削除 | なし |
| `todo` | セッション内で、doneは明確だがセッションをまたぐ追跡価値が無い実行項目を思いついた時（工数や行数ではなくdoneの定義を粒度の基準にする。doneが不明瞭なまま着手できてしまう問題を避けるため） | 自由に追記・削除。Handoffと異なりセッション境界の制約を受けない | 常に「今アクティブな項目」のみ。完了したら記録を残さず削除 | セッション境界（(1)(2)）で棚卸し。残っている項目はGitHub Issueかhandoffの「次にやること」へ移し、ファイルは空に戻す | GitHub Issue／`.dev/handoff.md`の「次にやること」 |
| GitHub Issues | doneの定義が明確で、かつセッションをまたぐ追跡価値がある実行項目が決まった時（粒度の基準の理由は`todo`行を参照）。無ければ`.dev/todo.md` | 状態・ラベル更新 | 1 Issue = doneの定義が明確な単位 | closeで完了。放置は定期的に棚卸し | `scratch`/Discussions/`.dev/todo.md`から移る |
| GitHub Discussions | 結論前の検討事項でメモの域を超えて残す価値がある時 | 追記（スレッド） | 特になし | 結論が出たら収束させ、closeしてよい | ADR/Issueへ |
