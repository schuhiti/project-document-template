# 文書化のルール

## 書いてよい内容の原則
- 文書には対象読者に関する事実のみを書く
- 対象外への言及は、読者自身の行動を制約する境界規定である場合に限り許容する
- 経緯・履歴は基本的に書かない。書く条件と扱いは「決定・経緯の記録」を参照
- 自動的に保証される性質（例:「このファイルは常時参照される」「Skillは自動読込される」）は自己言及的に書かず、実際にそれを担保する設定・確認作業を書く。未確認なら、未確認だと明示する
- 文書は確定した内容のみを書く。検討中のものは `.dev/scratch/` が保持し、`.dev/handoff.md` からはポインタのみで参照する。同じ文書の下書き版を並行して持つ必要はなく、確定分だけを都度反映して育てていけばよい
- 同じ情報を複数の文書に重複して書かない。特に「場所（パス）」はドキュメント参照表を正とし、他の文書では重複させずそちらを参照する
- `knowledge`の内容がSkillのルールとしても使われる場合、重複させず、可能ならSkill側への参照に置き換える。knowledge側に固有の説明が必要でどうしても内容が重なる場合は、対応するSkillの箇所を明記し、Skill更新時にknowledge側の確認要否を判断できるようにする
- 既存の不変な決定記録（ADR等）は、用語の定義・境界条件の再定義を含め、skill側で実質的に書き換えない。補正したい場合は、補正後の理解を通常の決定として反映先に直接書き、元の記録は不変のまま残す
- 他プロジェクトへ配布するテンプレートを含むプロジェクトでは、配布先へ同一内容のまま渡すファイル（`.agents/`配下等）に、配布先には無い前提（root/template分割等）を書き込んでいないか確認する。配布の仕組み自体は個別に記録する（例: `schuhiti/project-document-template`は`docs/knowledge/root-template-sync.md`に記録している）

## フロントマター規約
- 自前の文書種別（`premise`/`adr`/`knowledge`/`handoff`/`scratch`/`template`/`index`/`todo`）にはYAML frontmatterを付与する。必須は`type`のみ。`status`・`updated`・`tags`は種別に応じて任意
- `tags`はドメイン・性質による複数文書のグルーピングに使う。値を追加する前に、既存の文書と共有できる値かを確認し、共有先が無い一意の値（ファイル名やタイトルの言い換え等）は追加しない
- 独自の詳細なスキーマは設計しない（複雑さに見合う利益が無い）。frontmatterを完全に省く案も、将来的な検索性を損なうため採らない
- `todo`（`.dev/todo.md`）は`type: todo`のみで足りる。`updated`は更新頻度が高く鮮度追跡の意味が薄いため付与しなくてよい。最小形:
  ```
  ---
  type: todo
  ---
  # ToDo（セッション内）

  - [ ] 項目
  ```
- 外部で規約が確立している文書・ディレクトリは、その規約に従うことを優先し、本Skillの規約（frontmatter・index.md）の対象外とする
  - `AGENTS.md`（AGENTS.md仕様）
  - `CLAUDE.md`（Claude Code仕様。内容は`@AGENTS.md`のみ）
  - `.agents/`配下すべて（Agent Skills / AGENTS.mdエコシステムの標準構造）。ただし`SKILL.md`には横断検索のため`type: skill`・`updated`を追加で付与する（仕様と両立する）。Claude Code用の`.claude/skills`はここへのシンボリックリンク
- `docs/system.md`は`AGENTS.md`から切り出した指示の本体で、ドキュメント参照表を持つ文書そのもの。表に並ぶ種別のどれにも属さないためfrontmatter対象外
- `SETUP.md`等、使い捨てのオンボーディング文書は永続的な知識体系に属さないためfrontmatter対象外
- `README.md`等、ディレクトリの説明・ナビゲーション用の文書もfrontmatter対象外。`index.md`は機械的な一覧に限定するため、説明文はREADME側に書き分ける
- 対象外の一覧は本Skillが保持する。新たな対象外が生じた場合はここに追記する
- 各ディレクトリに軽量な`index.md`（`type: index`）を置く。ディレクトリを作る時点で一緒に用意する。ファイルを追加した際は、そのディレクトリの`index.md`にも1行追加する。ファイルを削除した際は該当行も削除する
  - `.agents/`配下は対象外
  - リポジトリ直下には`index.md`を置かない。ドキュメント参照表は「いつ何を読むか」のルーティング表であり、ファイル一覧ではない
- `index.md`の各行はMarkdownリンク記法`[ファイル名](ファイル名)`で書く（Claude Codeのhookが`](ファイル名)`の形で機械的に照合するため）。まだ存在しないファイル（`SETUP.md`実行前のpremise.md等）へのリンクも構わない

## 決定・経緯の記録

経緯は全ての決定について書かない。次のどちらかに当てはまる選択に限る。

- 後から蒸し返されるおそれがある（標準・既定の振る舞いから外れる選択は、たいていここに当たる）
- 記録しないと将来同じ時間を使って再発見する羽目になる

したがって記録が無いことは「検討していない」を意味せず、索引も決定の全集合ではない。索引にこの断りを書く。

書くと決めた後の扱いは次のとおり。決定の理由や却下した代替案が1〜2文で書けるなら、決定が反映される場所（documentation-rulesの該当箇所、knowledge等）にそのまま書き添える。独立したファイルは作らない。分量が増える場合（複数の論点、比較、詳細な理由）は独立したファイルに分け、決定が反映される場所には1行のポインタを残す。

独立したファイルの置き場所は確定度で決める。まだ議論中・確定前なら`scratch`（却下した方針とその理由を含む）、確定済みで残す価値があるなら`knowledge`。scratchのtriage先は`references/document-types.md`のscratch行を参照。

独立したファイルは次の4条件を満たす形で書く。

- 選択の記録だけを書く（採用した案と却下した案）
- 運用・ルールとして使う部分は生きた文書（premise・skill・knowledge等）側に置き、経緯側には残さない
- 現況の記述（構成の一覧、現在のファイル配置等）を含めない
- トリガー付きの保留を、本文にもポインタとしても含めない

4条件が揃った記録は、以後書き換える理由が無くなる。この状態になったものは不変として扱ってよく、内容が後から覆った場合も書き換えず、新しい記録を追加して古い記録を参照し、生きた文書側のポインタを新しい記録へ張り替える。ADRを運用するプロジェクトでは、この段階で`adr`として扱う（`references/document-types.md`のadr行を参照）。

理由: 経緯記録を可変のままにすると、決定が変わった時に古い理由が上書きされて消え、消えたこと自体を後から検知できない。運用と経緯が同じファイルに同居していると、不変にした時点で運用まで過去側に取り残される。保留は確定していないので、不変にすると再検討の結果と矛盾する。ポインタで持つ場合も、保留が決着すれば指し先の`scratch`が消え、張り替えられない死んだリンクが残る。

## 経緯への到達経路

到達経路は、生きた文書に残すポインタと、置き場所のディレクトリの`index.md`の2つだけ。`.dev/handoff.md`は完全上書きするのでポインタの置き場所にならない。同じ主題を再検討する時は生きた文書から入るので前者が効き、主題を跨ぐ場合と反映先を持たない却下の記録には後者しか届かない。決定を下す前に該当ディレクトリの`index.md`を読み、同じ主題の記録が既に無いか確認する。

ポインタは、その記録が説明している記述と同じ範囲に置く。文書全体が1つの決定の反映なら文書の冒頭に、文書内の特定の節だけが対応するならその節に置く。1つの文書に複数の決定が反映されているなら、対応する数だけポインタを置く。粒度を先に決めて統一すると、どちらかのポインタが対応関係を偽ることになる。ポインタには記録のファイル名を書く。「上の記録」のような相対的な指示は、周りの構成が変われば意味を失い、`check-adr-orphan.sh`の確認からも見えない。

反映先を持たない記録（却下・見送りだけを書いたもの、反映先が共有ファイルにあってポインタを置けないもの）は、本文に「到達経路: 索引のみ」の行を置く。`check-adr-orphan.sh`が、この行を持たない記録について生きた文書からのポインタの有無を確認する。

## 構成要素を追加・移動したときの登録先

文書体系の構成要素（新しい文書・ディレクトリ・種別・置き場所）を追加または移動したら、次を順に確認する。

- AIが読む契機があるか → あればドキュメント参照表に追加する。ただし自動的に読み込まれるものは、契機があっても載せない
- 属するディレクトリの`index.md`に1行追加したか
- 外部規約に従う文書なら、本Skillの対象外リストに追加したか
- 種別そのものを新設したなら、`references/document-types.md`に行を追加したか

## 文書種別ごとの運用

文書種別（premise/adr/knowledge/skill/scratch/handoff/template/index/todo、GitHub Issues/Discussions）ごとの書く契機・更新方式・サイズ規律・破棄条件・遷移先は `references/document-types.md` を参照。

本Skill本文自体が肥大化した場合、`references/`へ追加で切り出すことを検討する。
