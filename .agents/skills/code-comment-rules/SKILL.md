# コードコメントのルール

## 書かない内容
- 思考の過程・検討の経緯・作業履歴
- コードを読めば分かることの言い換え
- 変更の理由（コミットメッセージ・Pull Requestに書く）

## 書いてよい内容
そのコードを変更する人が、その場で知らなければ誤った変更をする内容に限る。

- 標準・既定の書き方から外れた選択の理由（Why NOT）
- 一時的例外と、その解除条件
- 外部要因による回避策（ライブラリの不具合、APIの制約）と、詳細を書いた文書へのパス

一時的例外には解除条件を書く。解除条件を書けないなら一時的例外ではないので、標準から外れた選択の理由として書く。

## 文書との使い分け
コメントを書く前に、文書側（`docs/knowledge/`・Skill）に書けないかを先に検討する。

- コードを読む文脈でだけ意味を持つ知見はコメントに書く
- コードから独立して意味を持つ知見（ドメイン概念、外部APIの仕様そのもの、設計判断）は文書に書く
- 同じ内容を両方に書かない。本体を文書に置いた場合、コメントからはパスで参照する

理由: コメントは対象のコードを読む人にしか届かず、コードが消えれば一緒に消える。文書は検索・参照できるが、コードを変更する瞬間には目に入らない。どちらに置くかは、その知見が必要になる瞬間がコードの上にあるかどうかで決まる。

コメントも文章なので、書き方は `writing-style-rules` に従う。
